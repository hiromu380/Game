# 週替わりチャレンジの運用

週替わりチャレンジ（コード内の名前は `weekly`）のスケジュール、定期ジョブ、失敗したときの対応、ローカルでの時刻送りをまとめる。
仕様は CLAUDE.md の「週替わりチャレンジ」、決めた経緯は docs/plans/weekly-challenge-plan.md。

## スケジュール

| 項目         | 既定値                                                 | 置き場所                                                                          |
| ------------ | ------------------------------------------------------ | --------------------------------------------------------------------------------- |
| 週の切り替え | 月曜 0:00（日本時間）                                  | `wrangler.jsonc` の `vars.CHALLENGE_OFFSET_MINUTES`（540）・`WEEK_START_DAY`（1） |
| 日の区切り   | 毎日 0:00（日本時間）。週の切り替えと同じずれを使う    | `CHALLENGE_OFFSET_MINUTES`                                                        |
| 週の通し番号 | `WEEKLY_EPOCH` の週が #1                               | `vars.WEEKLY_EPOCH`                                                               |
| 猶予         | 日・週の締め切りから 10 分（その日に始めた挑戦の提出） | `apps/server/src/config/weekly.ts` の `graceMs`                                   |
| 結果の確定   | 週の締め切り＋猶予＋15 分以降の Cron                   | `finalizeDelayMs`                                                                 |
| 保存期間     | 挑戦の操作ログ・日ごとの成績・確定した順位は 12 週     | `results.retentionWeeks`                                                          |

Next Fest などの会期に合わせて切り替えを変えるときは、`CHALLENGE_OFFSET_MINUTES`・`WEEK_START_DAY` を変えてデプロイする。
**週の途中で変えると、その週の締め切り・日の区切りがずれる**ので、週の切り替えの直後に変える。`WEEKLY_EPOCH` は変えない（週の番号が変わる）。

## 定期ジョブ（Cron 毎時。apps/server/src/jobs/scheduled.ts）

すべて冪等。失敗しても次の回で続きから進む。

1. **先行生成**（`prepare`）: 今週から 2 週先までの週を作る（床・ボス・特殊ルール・ショップのシード。相場はまだ入れない）
2. **公開前の自動検証**（`verify`）: 貪欲ボットが盤面を 3 回遊び、1 回でも全シフトをクリアできれば合格。
   不合格なら候補番号を進めて引き直し、8 候補まで不合格なら固定の代替設定（やさしい床の帯・特殊ルールなし）にする。
   Workers の CPU 上限に収めるため、1 回の Cron では約 250ms ぶんだけ進める（`verify.budgetMs`）。2 週先まで用意するので、時間は十分ある
   - 計画では「中級ボット」で検証する予定だったが、1 回の試行が CPU 上限に収まらないため、貪欲ボット（1 回 0.15 秒ほど）にした
3. **週の切り替え**（`open`）: 前週の購入率から相場を確定し、週の設定（RunConfig）に埋め込む。その週のうちは変えない
   - 相場の計算に失敗したら**基準価格で始める**（ログ: `market job failed, opening with base prices`。`weeks.market_state = 'base'`）
   - 検証が終わっていなければ**代替設定で始める**（ログ: `weekly board not verified before opening`）
   - Cron を待たず、その週の最初のアクセスでも開く
4. **結果の確定**（`finalize`）: 前週・前々週のベストを並べて順位・上位○% を保存する（500 件ずつ。途中で止まっても続きから）
5. **削除**（`purge`）: 保存期間を過ぎた挑戦・成績・確定した順位、IP ハッシュを消す

## 失敗の見つけ方と対応

| 症状・ログ                                                      | 意味                                                      | 対応                                                                                                                       |
| --------------------------------------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `/api/weekly/current` の `fallback: true`                       | 検証が間に合わず代替設定で開いた / 8 候補とも不合格       | 遊べるので急がない。8 候補とも不合格が続くなら、`pnpm balance --mode weekly` で原因（ノルマ・特殊ルール）を調べる          |
| `weekly board fallback week=…`                                  | 候補を使い切った                                          | 同上                                                                                                                       |
| `market job failed, opening with base prices`                   | 相場の計算に失敗して基準価格で開いた                      | その週はそのまま（公平性のため途中で変えない）。原因（D1 の障害など）を直す。翌週の相場は前週の集計から通常どおり作られる  |
| `scheduled jobs` のログが 1 時間以上出ない                      | Cron が止まっている                                       | 管理画面で Cron の実行履歴を確認する。止まっていても週は最初のアクセスで開く。結果の確定は Cron が戻ると前々週まで取り戻す |
| 結果発表がずっと「集計中」（`/api/weekly/<週>/results` が 425） | 結果の確定が終わっていない                                | Cron の履歴を確認し、必要なら管理画面から Cron を手動実行する（何度実行しても同じ結果）                                    |
| `weekly week has committed runs on an old sim`                  | 古い `SIM_VERSION` のまま開いた週に、確定済みの本番がある | 下の「古い SIM_VERSION のまま開いた週」                                                                                    |

### 古い SIM_VERSION のまま開いた週

`SIM_VERSION` を上げたデプロイが週の切り替えより後になり、その間に誰かが本番を確定した場合に起きる。
この週の提出は、デプロイ後すべて「バージョン違い」で拒否される（古いシミュレーションで確定した記録と混ぜないため）。

- 予防: `SIM_VERSION` を上げるデプロイは月曜 0:10 過ぎ（前週の猶予の後）にすぐ行う（docs/ops/deploy.md）
- 起きてしまったら: その週は前のバージョンに戻す（`npx wrangler rollback`）か、その週は諦めて翌週の切り替え直後に出し直す。
  どちらにするかは人が判断する（DB を手で書き換えて作り直すと、確定済みの記録との公平性が崩れる）

## ローカルで時刻を進めて試す

`apps/server/.dev.vars` に `DEV_CLOCK=1` を入れると、`POST /api/dev/clock` でサーバーの時計を進められる（localhost からだけ。本番では設定しない）。

```sh
cd apps/server
pnpm db:migrate:local
pnpm job all                   # 今週以降の盤面を用意・検証（しないと最初にアクセスした週は代替設定で開く）
pnpm dev                       # 別ターミナル。クライアントは pnpm dev（リポジトリのルート）

# 1. 今週のチャレンジを遊ぶ（ブラウザで）
# 2. 時計を 7 日進める（wrangler dev を再起動すると 0 に戻る）
curl -s -XPOST localhost:8787/api/dev/clock -H 'Content-Type: application/json' -d '{"advanceMs":604800000}'
# 3. 進めた時刻でジョブを実行する（--at はサーバーの時計に合わせる。/api/weekly/current の serverNow を ISO 形式にした値）
pnpm job all --at 2026-10-12T09:30:00Z
# 4. タイトルの「ランキング（先週）」に NEW が付き、今週のチャレンジを開くと結果発表が出る
```

- 1 日だけ進める: `{"advanceMs":86400000}`（翌日の挑戦・7 マスの表示を確かめる）
- 結果発表の既読はブラウザの `localStorage` の `chain-factory.weekly.resultsSeen`。消すと未読に戻る

## 設定（apps/server/src/config/weekly.ts）

- `provisional.topMode`: 暫定ランキングのトップの見せ方。`full`（実数）・`rounded`（上 3 桁に丸める。自分の出荷量は実数）・`hidden`（出さない）
- `provisional.cacheSeconds`: 暫定ランキングの並びをキャッシュする間隔（自分の順位は常に最新）
- 相場の係数（`config/market.ts`）: `smoothing` 0.7・参加者 50 人未満の週は据え置き・出現 100 回未満のパーツは据え置き
