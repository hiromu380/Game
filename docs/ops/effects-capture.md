# 連鎖演出の確認と録画

本番スイッチを押してから出荷量が確定するまでの演出（連鎖演出）を、規模別に再現・録画する手順と、設計の記録。

## 1. 仕組み

- 演出の流れは `apps/client/src/playback/choreography.ts` の `buildChoreography(events, 設定)` が決める（純粋関数。テストは `apps/client/test/choreography.test.ts`）
  - 入力は sim の events だけ。sim の結果・乱数には触れない（SIM_VERSION とは無関係）
  - 出力は tick ごとの長さと、演出の命令列（溜め・音階・倍率ポップ・桁上がり・ノルマ超え・光・ピーク・ドン）
- 数値（テンポ・上限・光の明るさなど）は `apps/client/src/config/effects.ts` の `choreography`
- 光の範囲と明るさの上限は docs/art-style.md「光の表現」

| 段階   | 内容                                                                                                      |
| ------ | --------------------------------------------------------------------------------------------------------- |
| 溜め   | 0.42 秒（強）。スイッチに光が集まり、低い音                                                               |
| 連鎖   | 1 tick 320ms から、連鎖するたびに 6% ずつ速く（最短 110ms）。1連鎖ごとに半音上がり、8段ごとに音色が変わる |
| 数字   | 倍率が乗ると「×2」「+3」が浮かぶ（最大30個・45ms 間隔で間引く）。桁の単位が変わると拡大と音               |
| ノルマ | 合計がノルマを超えた瞬間に帯「ノルマ突破！」・光・音                                                      |
| ピーク | 最後の出荷で 0.11 秒止まり（ヒットストップ）、最大の揺れ・光・音                                          |
| 余韻   | 最終スコアを盤面の中央に「ドン」と出す                                                                    |
| 上限   | 全体で 8 秒。超える連鎖は tick を縮め、それでも超えるなら最後の山場の手前まで一気に進める                 |

## 2. 規模別の演出時間（強・点滅を減らす=オフ、1×）

撮影モードのプリセット（`apps/client/src/config/capturePresets.ts`）で計った値。総時間は余韻（ドンの表示）を含む。

| 規模 | 連鎖数 | tick 数 |    出荷量 | 総時間（強／中／弱）   | ピーク（強） |
| ---- | -----: | ------: | --------: | ---------------------- | -----------: |
| 小   |      2 |       3 |         2 | 2.4 秒／2.2 秒／1.8 秒 |       1.2 秒 |
| 中   |      6 |       7 |        80 | 3.4 秒／3.2 秒／2.9 秒 |       2.3 秒 |
| 大   |     25 |      17 | 2,880,000 | 5.0 秒／4.8 秒／4.5 秒 |       3.9 秒 |
| 特大 |    259 |      39 |       200 | 6.6 秒／6.4 秒／6.1 秒 |       4.7 秒 |

7×7 の盤面で実際に組める連鎖は、発動回数の上限により 40 tick 前後で止まるため、上限（8 秒）には届かない。
200 tick 以上の人工的な events では上限で止まることを単体テストで確かめている。

## 3. 撮影モードでの確認・録画（人が行う作業）

```sh
pnpm --filter @chain-factory/client dev:capture   # 撮影モードで起動（http://localhost:5173）
```

1. 「はじめる」でランを始める（撮影モードのパネルが左下に出る。C キーで出し入れ）
2. パネルの「連鎖: 小／中／大／特大」で盤面を読み込む
3. 「このシードで本番」（シード 1）で再生する。シードが同じなら毎回同じ連鎖になる
4. 録画用には「ピークの直前から再生」に印を付ける: ピークの 1.5 秒前まで演出なしで進めてから再生するので、
   録画の最初の2秒に山場（ピーク・ドン）が入る（X の動画向け）
5. 再生速度 0.25×・0.5× でスローにもできる。UI の表示を「なし」にすると盤面だけになる
6. 設定画面の「演出の強さ（強・中・弱）」「画面の揺れ」「点滅を減らす」を切り替えて、見え方が変わることを確かめる

画面の録画は OBS などで行う（store-assets.md「トレーラー・GIF」）。

## 4. 性能

計測: Playwright（Chromium、1280×800）で、撮影モードの特大・大の盤面を再生し、requestAnimationFrame の間隔を記録した。
Steam Deck の代わりに CPU を 4 倍遅くした条件（CDP の `Emulation.setCPUThrottlingRate`）でも計った。

- 開発環境には GPU がなく、描画をソフトウェア（SwiftShader）で行うため、フレーム時間の絶対値は実機より大幅に悪い
  （何も再生していないときは 60fps。再生中は描画の負荷で 25fps 前後）
- JavaScript の処理は再生 8 秒のうち約 0.7 秒（1フレームあたり約 3ms）で、残りはソフトウェア描画だった
- 改善前（パーティクルを毎回作っていた版）と同じ条件で比べると、特大で 17.7fps → 25.1fps、CPU 4 倍遅いときは 9.3fps → 12.7fps（悪化はなし）

| 条件              | 改善前 fps | 改善後 fps |
| ----------------- | ---------: | ---------: |
| 大・1×            |       31.5 |       31.2 |
| 特大・1×          |       17.7 |       25.1 |
| 大・CPU 4倍遅い   |       18.4 |       19.4 |
| 特大・CPU 4倍遅い |        9.3 |       12.7 |

**実機（GPU のある PC・Steam Deck）での確認は人が行う**: 撮影モードで「連鎖: 特大」を本番再生し、
ブラウザの開発者ツール（Performance）か Steam のフレームレート表示で 60fps（Steam Deck は 60fps か、少なくとも 40fps）を保つことを確かめる。
