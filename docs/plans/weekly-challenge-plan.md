## 1. 先に指摘しておきたいこと（異論・懸念・より良い案）

1. **本番シードは「日ごと」に変える（公平性）**
   - 今のデイリーは `本番シード = HMAC(dailySecret, shiftIndex)`。これを週の ID だけで作ると、1日目の挑戦で返ってきた本番シードを、2日目以降の挑戦でそのまま使える（ポンコツロボの乱数が完全に読める）。
   - 提案: `本番シード = HMAC(weekSecret, dayId ‖ shiftIndex)`（**不採用**: 週ごとのシードに決定）。同じ週の同じ日は全員同じシードで、日が変わると変わる。盤面・ショップ・試運転は1週間同じなので「1週間かけて攻略する」は保たれ、ランダムな動きには毎日少し違う結果が出る。
2. **盤面の自動検証は「サーバーの定期ジョブで少しずつ」動かす（CPU 上限との兼ね合い）**
   - ボットの重さ（デイリー条件・1ラン）: 貪欲 0.15 秒・中級 0.48 秒・探索 1.78 秒（`pnpm balance --mode daily` の計測）。
   - Workers の CPU 上限は、料金の暴走防止で 500ms にしている（定期ジョブも同じ上限）。探索ボットは入らない。
   - 提案: 検証は **貪欲・中級ボット**で行い、1回の定期実行（毎時）で処理する量に予算（既定 300ms）を持たせる。途中までの結果は DB に保存し、次の回で続きを処理する。週の開始の 3 日前から先行生成するので、72 回分の余裕がある。
   - 合格の基準（案）: 中級ボットが 3 つの本番シードのうち 1 つ以上で全シフトをクリアし、かつ貪欲ボットが 3 つのうち 2 つ以上で 2 シフト以上をクリアする。参考までに、今のデイリーの条件では中級ボットの全クリア率は 57%、探索ボットは 70% です。
   - 再抽選の上限は 8 回。上限に達したら、テストで合格を確かめておいた**固定の代替設定**（ステージの帯と週の ID から作る、決まった数件）を使う。
   - ボットは今 `tools/balance` にあり、製品コードから使えない。**`packages/bots` に切り出し**、サーバーの検証と `tools/balance` の両方から使う（依存は sim だけ。CLAUDE.md の構成に追記）。
3. **暫定ランキングの「自分の順位」は、キャッシュした並びから二分探索で求める（D1 の読み取り量）**
   - 今のやり方（自分より上の件数を SQL で数える）だと、1 回の表示で平均して参加者の半分の行を読む。参加者 1 万人・1 人 1 日 5 回表示だと、1 か月で約 75 億行になる（Workers Paid の込みの量は 250 億行）。
   - 提案: その週のベストの並び（並び順のキーとプレイヤー ID だけ）を 60 秒ごとにまとめて読み、キャッシュに置く（1 万人なら約 400KB）。トップ 10・参加人数・自分の順位は、このキャッシュから求める。読み取りは 60 秒に 1 回 × 参加人数（1 万人で 1 か月約 4.3 億行）で済む。
   - キャッシュは Cloudflare の Cache API をアダプター層に隔離し、テストはメモリーで代用する（AWS 移行を見据えたルール）。
4. **確定（結果発表）は、締め切り＋猶予のあとに分けて処理する**
   - 参加者全員の順位を保存するので、1 万人なら 1 万行を書く。1 回の定期実行に収まらない可能性があるため、続きから再開できる形（処理済みの位置を保存）にする。何度実行しても同じ結果になる。
5. **日・週の境目をまたいだ挑戦**（提案）
   - 挑戦は「始めた日」のものとして数える。本番の提出は、その日の締め切り＋猶予（既定 10 分）まで受け付ける。週の最終日に始めた挑戦は、その週の分として、週の締め切り＋猶予まで受け付ける。
   - 猶予を過ぎたら、その挑戦はそこまでの成績で終了する（今のデイリーと同じく、途中までの成績もランキングに載る）。確定ジョブは、締め切り＋猶予＋余裕（15 分）のあとに動かす。
6. **相場を週次にすると、動きがゆるやかになる**
   - 更新は年 365 回から年 52 回に減る。代わりに 1 回あたりのデータは約 7 倍になり、ばらつきは小さくなる。
   - 係数の案: 移動平均の新しい値の重みを 0.5 → 0.7（反応を少し速く）、据え置きの閾値を参加人数 20 → 50 人、パーツの出現数 30 → 100 回にする。
   - 相場のジョブが失敗したら、その週は基準価格で始め、週の途中では変えない（手順を docs/ops に書く）。
7. **「週の合計」ではなく「週のベスト」で並べる**（プロンプトの見立てに同意）
   - 出荷量の桁が極端に大きいので、合計してもベストとほぼ同じ順位になる。複雑さが増えるだけで、合計にする理由はない。
8. **上位の点数が見えることのリスクと切り替え手段**
   - リスク: 後から始めた人が、上位の点数を見て諦める。上位の顔ぶれが固定化する。
   - 対策: トップ 10 の表示を設定値で `実数`（既定）・`桁の丸め`（例: 3.2億）・`非表示`（自分の順位と上位○%だけ）の 3 つから切り替えられるようにする。表示名は自動生成の名前だけで、非表示フラグ（不適切な名前）は表示のときに反映する。
   - 週の終わり際の演出（提案のみ・今回は作らない）: 「締め切りまで あと○時間」の表示と、「暫定順位が○位上がった／下がった」の通知（前回見たときの順位を端末に覚えておく）。
9. **実績「上位○%以内」は、確定した結果でだけ解除する**
   - 当週の暫定順位は変わるので、解除は翌週の結果発表を見たときに行う（サーバーで確定済みの値を使う）。参加日数の実績・統計は今まで通り。

## 3. 計画

### 3.1 週と日の定義（設定値: `apps/server/src/config/weekly.ts`。sim 側の同じ値は `packages/shared`）

- 週の ID = 週の開始日（日本時間の月曜の日付 `YYYY-MM-DD`）。日の ID = その日の日付。
- 切り替えの曜日・時刻と、UTC からのずれ（540 分）は設定値。今のデイリーと同じく、タイムゾーンのデータベースは使わない。
- 時刻はすべてサーバーの `ctx.now()` で判定する。ローカルでは時刻を進められる仕組みを用意する（3.7）。

### 3.2 DB スキーマ（Drizzle。text と integer だけ。SQLite 固有の機能は使わない）

| テーブル                      | 主キー                       | 中身                                                                                                                                                                                   |
| ----------------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `weeks`                       | `id`（週の ID）              | 通し番号・相場を入れる前の RunConfig・再抽選の回数・検証の状態（`pending`／`verified`／`fallback`）・相場を入れた RunConfig（確定後）・シードの証明・SIM_VERSION・受付期間・確定の状態 |
| `week_verifications`          | 週の ID＋候補番号＋試行番号  | 検証の途中結果（どのボット・どの本番シードで何シフトクリアしたか）                                                                                                                     |
| `weekly_attempts`             | 週の ID＋日の ID＋プレイヤー | その日の挑戦の操作ログ・シフト番号・状態（1 日 1 回を主キーで保証）                                                                                                                    |
| `weekly_attempt_results`      | 同上                         | 挑戦ごとの成績（スコアの 3 列・クリアしたシフト数・最大連鎖・提出時刻）                                                                                                                |
| `weekly_bests`                | 週の ID＋プレイヤー          | その週のベスト（並び順のインデックスつき）・ベストの日・参加日数                                                                                                                       |
| `weekly_standings`            | 週の ID＋プレイヤー          | 確定した順位・上位○%（千分率）・スコア・参加日数。上位 100 件はここから読む                                                                                                            |
| `weekly_finalizations`        | 週の ID                      | 確定の進み具合（処理済みの位置・参加人数・確定時刻）                                                                                                                                   |
| `shop_stats`・`market_prices` | 日 → **週**の ID に変更      | 相場の材料・その週の相場                                                                                                                                                               |

- 書き込みの見積もり（1 万人・1 人あたり週 4 回挑戦）: 挑戦 4 万行＋成績 4 万行＋ベストの更新＋確定 1 万行。1 週あたり十数万行で、Workers Paid の込みの量（5000 万行／月）に十分収まる。
- 保存期間（12 週）を過ぎた挑戦の操作ログと順位は、定期ジョブが削除する。

### 3.3 API（`/api/weekly/*`）

| メソッド・パス                            | 内容                                                                                                                                                       |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /weekly/current`                     | 今週の情報（RunConfig・シードの証明・受付期間・今日の日の ID・次に挑戦できる時刻）。ログインしていれば、自分の今週のベスト・挑戦済みの日・今日の状態も返す |
| `POST /weekly/:week/attempts`             | 今日の挑戦を始める（すでに挑戦していれば「今日は挑戦済み」）                                                                                               |
| `GET /weekly/:week/attempts/:day`         | 自分のその日の挑戦の途中経過（再開用）                                                                                                                     |
| `POST /weekly/:week/attempts/:day/commit` | 本番 1 シフト分の検証と確定。結果に「今週のベストを更新したか」を含める                                                                                    |
| `GET /weekly/:week/provisional`           | 暫定ランキング（当週だけ。参加人数・トップ 10（設定に従う）・自分の暫定順位と上位○%）。**他人の配置・操作ログは含めない**                                  |
| `GET /weekly/:week/results`               | 確定ランキング（締め切り後の週だけ。当週・未来週は「まだ公開されていません」、確定前は「集計中」）。上位 100 件・自分の順位・前後数件                      |
| `GET /weekly/:week/results/:rank/replay`  | 確定後の週だけ: 上位の挑戦の操作ログと本番シード（リプレイ用）                                                                                             |
| `GET /weekly/:week/reveal`                | 締め切り後に週の秘密値を公開（シードの証明と照合できる）                                                                                                   |
| `GET /weekly/latest`                      | 最新の確定済みの週の ID（タイトルの未読バッジ用。とても軽い）                                                                                              |
| `/api/daily/*`（旧）                      | 410 と「アプリを更新してください」を返す                                                                                                                   |

- SteamID などの個人を特定しうる情報は、どのレスポンスにも含めない（今まで通り）。
- 当週の他人の提出データを返す API は作らない。テストで確かめる。

### 3.4 ジョブ（トリガーから独立した関数。何度実行しても同じ結果。毎時の Cron と、手動の `job` コマンドで実行）

1. **先行生成**: 3 週先までの `weeks` を作る（相場を入れる前の RunConfig）。
2. **検証**: 未検証の週を、予算の範囲で少しずつボットにかける。不合格なら再抽選し、上限に達したら代替設定を使う。
3. **相場の確定**: 週の切り替えの直後に、前週の購入率から相場を計算して、今週の RunConfig に埋め込む。その週の最初のアクセスでも実行する。失敗したら基準価格で確定する。
4. **結果の確定**: 締め切り＋猶予＋余裕のあとに、前週の順位を確定する。続きから再開できる。
5. **後片付け**: 保存期間を過ぎたデータと IP のハッシュを削除する（既存）。

失敗の検知（ログの警告と、`weeks`・`weekly_finalizations` の状態）と、再実行の手順は `docs/ops/weekly.md` に書く。

### 3.5 画面（React。文言はすべて i18n）

- **タイトル**: 「今週のチャレンジ」と「ランキング（先週）」。新しい結果発表をまだ見ていなければバッジを出す（最後に見た週の ID は端末に保存。セーブデータとは別）。
- **チャレンジ画面（挑戦前）**: 今週の条件（特殊ルール・ボス）、今週の自分のベスト、挑戦済みの日（月〜日の 7 マス）、次に挑戦できる時刻、本番・練習のボタン、暫定ランキング（「暫定」を常に明示）。
- **結果発表**: 前週に参加していて未読なら、チャレンジ画面を開いたときに演出つきで出す（順位・上位○%・ベスト・クリアしたシフト数・参加日数・上位の一覧・自分の前後）。参加していなければ上位の一覧だけ。初週は「結果発表は来週」。集計中は待機表示にし、間隔を空けて自動で取り直す（上限あり）。「共有」ボタンを置く。
- **挑戦の直後**: 出荷量・クリアしたシフト数・今週のベストを更新したか・「今日の挑戦は完了（次は明日 0:00）」・「結果発表は来週の月曜 0:00」・暫定順位と上位○%（前回からの変化つき）。
- **共有カードに渡すデータ**: `{ weekId, weekNumber, rank, topPercent, bestScore, shiftsCleared, daysPlayed, provisional }`（カードの描画は共有カードの担当）。

### 3.6 sim・shared の変更

- `buildDailyConfig` → `buildWeeklyConfig({ weekId, prices, practice, candidate })`。ランシード = `hash('weekly:' + weekId + ':' + 候補番号)`。
- RunConfig の `mode: 'daily'` → `'weekly'`、実績の条件（`dailyDays` など）も改名する。セーブデータの記録の名前が変わる場合は `SAVE_VERSION` を上げて変換する。
- 上限（生成の試行回数・検証の予算・操作ログの最大長・再生の最大 tick 数）は設定に集め、上限に達したときの回帰テストを足す。
- `SIM_VERSION` を上げる（RunConfig の作り方が変わるため）。

### 3.7 ローカルで確かめる仕組み

- `.dev.vars` に `DEV_CLOCK=1` があるときだけ、`POST /api/dev/clock`（時刻を進める・戻す）を有効にする。本番の設定には書かず、ホスト名が localhost 以外なら無効にする。
- ジョブは今まで通り `--at` で時刻を指定して実行できる。
- 手順（週の生成 → 挑戦 → 暫定順位 → 日・週を進める → 結果発表）は `docs/ops/weekly.md` に書く。

### 3.10 マーケティング連携（提案のみ）

- **週次の X 投稿**: 「先週の結果発表」の上位の挑戦は、保存した操作ログと本番シード（週の秘密値は公開済み）を sim で再生すれば、連鎖を同じように再現できる。撮影モードに「リプレイを読み込む」を足せば、録画に使える（実現できる見込み。必要な材料はすべて保存している）。
- **Next Fest**: 週の切り替えの曜日・時刻は設定値なので、会期（約 1 週間）に合わせられる。

## 4. テスト

プロンプトの「テスト」と「無限ループ・無限増殖の防止」をすべて入れる。主なもの:

- 週・日の境目（日本時間 0:00、月曜 0:00 の前後。猶予の内外）、1 日 2 回目の提出の拒否、同時提出・二重提出
- 週のベストの選択・同点・参加日数、当週・未来週のランキングが取れないこと、当週の他人の配置系のデータが返らないこと
- 暫定ランキングの並び・同点・参加者 0 人・1 人、キャッシュの間隔、暫定から確定への切り替わり
- 確定ジョブの冪等性・途中失敗からの再開、相場のジョブが失敗したら基準価格で始まること、盤面の再抽選と代替設定への切り替え
- 非表示フラグを確定後に付けても表示から外れること、結果発表の画面状態（参加した・しない・初週・集計中・未読・既読）
- 買って売るのを繰り返してもお金が増えないこと（ボット）、循環する盤面が有限で止まること（既存のテストを週替わりの設定でも回す）
